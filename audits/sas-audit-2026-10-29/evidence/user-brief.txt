# SECTION 2 — NON-NEGOTIABLE EXECUTION PRINCIPLES

These requirements govern every phase of the investigation.

## 2.1 Inspect the actual plugin

Inspect the real SOFTWARE ARCHITECT STUDIO implementation and all relevant accessible materials.

Do not evaluate only the plugin's intended design or its marketing description.

Investigate the actual files, skills, instructions, configurations, tool definitions, schemas, workflows, tests, fixtures, reports, documentation, and integration points available in the environment.

If a component cannot be inspected, record it as an inspection limitation.

## 2.2 Establish evidence before drawing conclusions

Classify every significant finding as one of the following:

- **Verified defect:** A reproducible problem demonstrated through inspection or testing.
- **Verified capability:** Functionality directly confirmed through inspection or execution.
- **Documented capability:** Described in documentation but not independently verified.
- **Demonstrated limitation:** A capability was attempted under known conditions and failed or proved unavailable.
- **Evidence-backed risk:** A credible potential failure supported by implementation evidence.
- **Inferred concern:** A reasoned conclusion that still requires verification.
- **Missing capability:** A capability absent from the inspected scope, with the limits of that inspection stated.
- **Improvement opportunity:** An existing capability that could provide greater value.
- **Experimental proposal:** A potentially valuable idea that requires feasibility or value validation.
- **Unknown:** Insufficient evidence exists for a reliable conclusion.

Do not confuse an inaccessible implementation with a nonexistent one.

Do not confuse an instruction that tells an AI to perform a task with a tool that actually performs and verifies that task.

## 2.3 Genuine independent agents only

Create ten genuinely separate AI subagents if the available environment supports real agent creation and execution.

Prefer independent parallel investigations where feasible.

If native subagents are unavailable, perform ten clearly separated specialist-role analyses without claiming that they were independently executed agents.

Record:

- The actual number of agent instances created.
- Whether their execution was parallel or sequential.
- How independence was maintained.
- Which findings were independently reached.
- Which findings emerged only during synthesis.
- Which tests or tools each agent actually used.

Do not fabricate independent perspectives, agent communication, or parallel execution.

## 2.4 Be exhaustive without manufacturing findings

There is no arbitrary limit on meaningful findings.

Investigate every materially relevant category.

However, do not produce weak recommendations merely to increase the report's length.

Depth means root-cause analysis, supporting evidence, alternative solutions, trade-offs, implementation details, and validation—not repetition.

## 2.5 No unnecessary rewrites

Do not assume a full redesign or complete rewrite is desirable.

Prefer the smallest change that adequately addresses the underlying problem, unless evidence demonstrates that the existing architecture cannot reasonably support the target capabilities.

Evaluate incremental improvement, targeted refactoring, modular redesign, and replacement as competing options.

## 2.6 No unsupported autonomy

Distinguish between:

- Reasoning about an action.
- Recommending an action.
- Generating an artifact.
- Preparing an executable change.
- Executing a change.
- Verifying the outcome.

Do not claim that code was built, tested, deployed, or executed unless the corresponding action actually occurred and its result was observed.

## 2.7 Preserve the existing plugin during the audit

This assignment is an audit, analysis, and redesign-planning exercise.

Do not modify, overwrite, delete, publish, deploy, or reconfigure the existing plugin during this investigation.

Read-only inspection and safe, non-destructive tests are permitted where supported and authorized.

You may prepare audit reports and proposed specifications separately from the plugin's existing implementation. Do not replace production or project files with proposed changes.

The resulting blueprint must be ready to guide a subsequent, explicitly authorized implementation phase.

## 2.8 Use available tools honestly

Enumerate the actual tools, permissions, integrations, and execution capabilities available.

Do not assume that a browser, shell, repository connector, compiler, deployment environment, native agent framework, or external validator exists.

Where a capability is unavailable, specify:

- What cannot currently be done.
- Why it cannot be done.
- What could still be accomplished.
- What additional capability would be required.
- Whether the proposed extension is worthwhile.

## 2.9 Maintain traceability

Assign stable identifiers to significant findings and recommendations.

Every major recommendation must trace back to one or more findings, and every implementation initiative must trace back to the recommendations it addresses.

The report must make it possible to move from an observed problem to a proposed solution, implementation specification, test plan, and measurable acceptance criteria without losing the reasoning behind the decision.

## 2.10 Investigate the wider plugin ecosystem

Do not assume SOFTWARE ARCHITECT STUDIO must implement every capability itself.

Investigate other available plugins, specialized tools, integrations, and developer products that could complement or extend its capabilities.

Evaluate whether each valuable capability should be built into the Studio, accessed through an existing integration, provided by an optional companion plugin, or rejected.

Never assume that a plugin is installed, available, compatible, or authorized merely because it appears in a search result or directory.

Do not install, activate, connect, authorize, or configure external plugins without explicit authorization.

## 13.5 Apply the four-way integration decision framework

Every significant capability or candidate integration must receive one primary recommendation:

### Decision A — BUILD IN

Implement the capability directly within SOFTWARE ARCHITECT STUDIO.

Choose this when native implementation offers a defensible advantage in:

- Core architectural reasoning.
- Project state and decision management.
- Skill routing.
- Requirements traceability.
- Cross-artifact consistency.
- Change-impact reasoning.
- Central workflow coordination.
- Other capabilities that should remain under the Studio's direct control.

Do not choose native implementation automatically.

Assess whether the development and maintenance cost is justified and whether the required tools and infrastructure are available.

### Decision B — INTEGRATE

Connect to an external plugin, connector, API, or developer tool so the Studio can use its capabilities.

Choose this when an existing specialist tool provides substantial value and can be integrated safely and reliably.

Specify:

- Integration boundary.
- Required permissions.
- Inputs and outputs.
- Data flow.
- Authentication requirements.
- Error handling.
- Version compatibility.
- Validation.
- Failure recovery.
- Maintenance.
- Security implications.

### Decision C — USE ALONGSIDE

Recommend an optional companion plugin or tool for specialized workflows that do not require deep integration.

Choose this when the external tool is valuable but a direct integration would add unnecessary complexity, cost, risk, or maintenance.

Specify:

- The specific task for which the companion is useful.
- What SOFTWARE ARCHITECT STUDIO should do before using it.
- What information should be transferred.
- What artifacts or results should return to the Studio.
- How the user can verify the external result.
- Whether the workflow can remain entirely manual.

Do not assume companion tools can automatically exchange information.

### Decision D — DO NOT ADOPT

Reject the capability or integration when:

- It duplicates an existing capability without meaningful improvement.
- Its quality cannot be established.
- It requires disproportionate complexity.
- It introduces unacceptable security or privacy risks.
- It creates unnecessary vendor lock-in.
- It depends on unavailable permissions or infrastructure.
- It has unsuitable maintenance or operational costs.
- It does not address a demonstrated user need.
- A simpler alternative is clearly preferable.

Explain the rejection and identify any circumstances that might justify reconsideration.

A capability may be valuable in principle but unsuitable for the current implementation. Preserve that distinction.
