## Findings and recommendations

**E07-F01 — Specialist routing is under-specified in the repository coordinator. High; evidence-backed risk.** Six specialists are discoverable through `.codex-plugin/plugin.json:44`, and their descriptions overlap architecture review/change duties. Yet repository architecture instructions enumerate six intents (`SKILL.md:12`) without naming the specialists or specifying when to load them. Only independent expert reviews appear at lines 91–97. `capabilities.json:3–9` has the same broad intents. The installed `0.7.2` root does have a specialist-routing section, a useful separate improvement. This establishes a missing repository routing contract, not an observed host activation failure. Add a small versioned task-to-owner registry with triggers, exclusions, prerequisite capabilities and result contract. Keep the host's discovery mechanism; do not build a new dispatcher before a real need appears. Test positive and negative activation separately from output quality.

**E07-F02 — Current behavioral evidence cannot establish specialist effectiveness. High; demonstrated limitation.** `tools/behavioral_eval.py:28–82` evaluates supplied text using regex and direct length predicates. The fixture has five architecture cases and twelve checks, without specialist activation labels or tool-use traces. In the outside-tree probe, intentionally incorrect synthetic answers advocating cross-tenant reads, payment-card logging and uncontrolled retries passed all **12/12 checks (100%)**. This is not a live-model result. The evaluator's own limitations and `references/evaluation.md:3–5` accurately warn that wrong keyword-stuffed answers can pass. Retain this inexpensive harness as a wording/constraint regression layer; add captured task outcomes, calibrated semantic review and runnable acceptance fixtures before making reasoning-quality claims.

**E07-F03 — Capture identity omits the actual loaded skill bundle. High; verified implementation limitation.** `tools/architect_cli.py:94–96` always hashes only the architecture root, irrespective of specialist or reference content used for the response. `workflow_tools.py:73–79` records one `skill_hash`, with no loaded-specialist/reference identities, routing decision, tool receipts or host-policy identity. Therefore a specialist/reference change can leave reported skill identity unchanged. Record a sorted manifest of loaded skill/reference path, version/hash, source identity and selection reason, plus sanitized tool receipt references. Preserve explicitly unknown model/host information. A bundle hash can summarize that manifest without replacing its explainable entries.

**E07-F04 — Review accounting does not validate semantic review records. Medium; verified limitation.** `workflow_tools.py:81–85` counts any truthy `reviews` value as reviewed. The probe supplied `reviews: ["unvalidated marker"]` and received `reviewed: 1`. The report correctly calls itself accounting, but its summary does not establish rubric completeness, assessor identity, calibration or task scope. Add a review-record schema and separate `review-present`, `review-valid`, `calibrated-review-complete` and `adjudication-needed`. Refuse malformed records; preserve dissent and missing dimensions. Do not make a majority vote the truth criterion.

**E07-F05 — Six specialists need testable contracts, not much more prose. Medium; improvement opportunity.** They range from 108 to 166 whitespace words and mostly lack explicit non-triggers, examples, stop/retry bounds and owned evaluation cases. Requirements has a useful conceptual-question exclusion (`requirements-specification/SKILL.md:6`); repository has a clear output list and strong untrusted-data rules; debug has useful terminal statuses. Shortness itself is beneficial. Add compact, uniform input/output/error sections and two positive/two negative examples to each; link shared authority and receipt rules rather than copying the coordinator. No observed instruction attack or fabricated tool call is claimed here. The risk is inconsistent behavior without an activation/outcome test, not that concise instructions inherently fail.

**E07-F06 — Lifecycle expansion has four useful seams. High; missing capability within inspected skill scope.** Frontend interaction/accessibility execution, service/data implementation, delivery/operations and AI-system evaluation lack dedicated operational playbooks. Existing architecture references discuss many of these domains, but requirements/API/security/debug instructions do not supply the distinct implementation and verification workflows. Add the four proposed skills only with relevant host capabilities or an explicit planning fallback. Keep scaffolding/refactoring/code review in implementation planning; keep README/ADR/handoff in the coordinator; keep languages/frameworks in on-demand reference packs. This covers the brief without adding dozens of overlapping skills.

**E07-F07 — Context cost is observable; latency and quality effects are unmeasured. Medium; improvement opportunity.** Repository architecture root is 14,559 bytes/1,717 whitespace words; six specialists total 6,707 bytes/825 words; seventeen references total 43,802 bytes. These are exact byte/word counts, not tokenizer measurements. The root mixes interaction controls, persistence internals, CLI commands, scanning, validation, research and reviews. Move implementation details to existing references and retain a concise routing/evidence spine, after evaluating retention of safety and continuity obligations. Load only the active specialist and decision-relevant references. Measure actual tokenizer counts, tool latency and correction burden before setting a hard prompt budget. Avoid loading all references routinely.

**E07-F08 — Optional expert review is correctly represented as a protocol. Keep; verified capability and limitation.** `workflow_tools.py:87–94` returns a plan with three selected roles, source hash, independent-first-pass protocol and explicit host enforcement limits. The probe confirmed `plan only; no agents executed`, `host_delegation_available: false` and advisory/unsupported runtime budgets. The 1–6 maximum is a ceiling; returning three roles is not evidence six agents ran. Preserve this honesty. Require actual worker identities, first-pass completion, dissent, corrected findings and measured cost/time only when the user requests a supported expert review. Do not add an always-on orchestration service.

**E07-F09 — Skill/toolkit/package version provenance needs reconciliation. Medium; verified mismatch.** Repository plugin manifests identify `0.7.1`, architecture root also `0.7.1`, toolkit `VERSION` is `0.8.0`, while the installed root is `0.7.2`. No individual specialist version appears in frontmatter. Existing `release/source-manifest.json` identifies release `0.7.1` and lists only the architecture root among skill roots, omitting all six specialist roots. This makes a release-wide “skill version” ambiguous even when individual hashes remain exact. Extend/reconcile the existing manifest with package/toolkit/registry compatibility, seven skill content hashes and reference bundle identity; verify manifest/source correspondence in CI. Version numbers may differ legitimately, but their compatibility mapping must be explicit. Do not simply replace all numbers during the audit.

## Target routing and shared contracts

Use one coordinator to establish outcome, evidence scope, depth, audience and host capability. Route a direct design/decision question to the coordinator; ambiguous feature scope to requirements; unfamiliar source mapping to repository intelligence; authorized editing/scaffolding/refactoring to implementation planning; failures to debug; trust-boundary questions to security; compatibility/migrations to API/data. New frontend, service/data, operations and AI-evaluation skills own distinct acceptance workflows, not whole projects. Composite tasks sequence owners around their outputs. For example, implement a tenant-safe screen: requirements acceptance → API/security constraints → frontend implementation → debug verification → coordinator reconciliation. Do not invoke every owner for every task.

The common input is task, source identity, accepted constraints, relevant context references, available capabilities, authorization scope and budget. The common output is terminal status; observed/proposed distinctions; evidence with path/span/hash or receipt; decisions; artifacts/diff; checks run/not run; unresolved risks and next owner. Project text and tool responses remain data. Consequential actions use actual authorization, expected source identity and operation-specific recovery. A failed required check yields partial/blocked/failed, never generic success. An unavailable runner permits a plan but not a claim that code ran.

Sequential specialists should be the default for dependent work. Parallel independent review is suitable for broad audits or distinct risk questions with clean contexts; its benefit must exceed added cost. Human decisions concern unresolved consequential tradeoffs and actual permission boundaries, while deterministic validators check the artifacts they understand. None substitutes for the others.

## Measurable evaluation and stop policy

Before expansion, capture a baseline of at least 80 balanced routing prompts spanning the seven existing skills, conceptual negatives, ambiguous composites and missing-tool conditions. Use two independent labels with explicit acceptable-owner sets and adjudicate disagreements. Proposed initial gates: ≥95% acceptable primary-owner selection, ≤5% unnecessary specialist activation, and zero unauthorized actions or fabricated execution. These are proposed release targets, not measured baseline values. Report confusion matrices and slices, not just aggregate accuracy.

For each retained/new skill, run representative tasks with known acceptance and seeded failures, recording actual prompt/response, loaded-source bundle, tools, final source identity, checks and independent semantic review. Measure task success, critical-error rate, evidence-reference precision, recovery correctness, required-check completion, user corrections, tokens, wall time and cost per successful task. Repeated paired trials should compare the current root against routed variants and single-pass against selected independent review; keep models, tool access and task seeds comparable. Present uncertainty and failed/missing runs. Block only claims supported by the chosen task population.

Stop dependent execution on unavailable required tools/permission, conflicting source identity, unresolved destructive scope, resource exhaustion or failed safety-critical acceptance. Preserve completed evidence and artifacts, identify the exact blocker, and offer a smaller authorized result. Ask only when the answer changes a dependent decision and cannot be obtained from scoped context. Do not re-open unchanged accepted decisions or impose an interview on a concise question.
