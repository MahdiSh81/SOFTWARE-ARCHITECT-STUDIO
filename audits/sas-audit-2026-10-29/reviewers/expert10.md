It does not establish measured improvement in architecture reasoning, representative task success, specialist benefit or user outcomes. **Verified capabilities:** selected recovery, conflict, restore, handoff identity, reference validation, cache and capacity regressions execute successfully. The CLI records a source hash and revision, preserves unknown approval origin instead of inventing an approver, excludes raw history/extensions from continuation packets, and states that acceptance grants no tool authority. ## Findings

### E10-F01 — Release evidence does not identify one current package (P1, verified defect)

`README.md:1` and `tools/project_model.py:6` identify 0.8.0; `plugin.json`, `.codex-plugin/plugin.json`, `capabilities.json`, `IMPLEMENTATION_STATUS.json`, `CHANGELOG.md` and `release/verification.json` still identify 0.7.1. Git shows the actual change sequence: initial imported toolkit, `6998867` validation/evidence changes, `061952e` specialist skills/browser CI, merge, then two README changes. There is no source-backed basis to call the old 77-test/25-Node receipt a current 0.8.0 verification.

The source manifest explicitly says “All packaged files except this manifest.” Six of its 67 tracked hashes differ from current bytes, and new skill, contract and CI files are not inventoried. `.github/workflows/ci.yml:32` invokes `tools/check_source_manifest.py --check`; that file does not exist. This is a deterministic CI failure once the job reaches that step, independently of network/browser availability.

**Recommendation GOV-01:** choose the intended current version, align both manifests and reported runtime version, retain historical receipts under their version, and generate a current source inventory and check receipt pinned to the Git commit and dirty overlay. Add the missing checker or change CI to the supported inventory check. Acceptance: one consistent package version; zero unexpected inventory differences; the exact declared CI command exists and passes; previous receipts remain explicitly historical. Do not “fix” this by relabeling an old receipt.

### E10-F02 — ADR supersession does not maintain lifecycle/provenance invariants (P1, verified defect)

`tools/project_model.py:102–109` and `workbench/project-core.js:46` clone the whole predecessor. Superseding `ADR-001` to `ADR-002`, then superseding `ADR-001` again to `ADR-003`, produces a Proposed `ADR-003` with `superseded_by: ADR-002`; both successors say they supersede `ADR-001`, whose backlink now names only `ADR-003`. `project_checks` returns no errors. It also accepts an Accepted decision referring to nonexistent `supersedes`/`superseded_by` IDs and `approval_origin: false`; `resume_packet` forwards that false value.

The first successor also inherits the predecessor’s `approval_origin`, although its status becomes Proposed. This does not grant execution authority, and inherited history can be useful, but approval of the old decision is not approval of a new one. Current predecessor-preservation tests do not cover repeated supersession, dangling lifecycle references, cycles or approval attribution.

**Recommendation GOV-02:** define a narrow lifecycle contract shared by Python and JavaScript. Reject repeated successor creation unless branching is deliberately modeled; validate lifecycle IDs, self-links, cycles and reciprocal relations; distinguish predecessor provenance from successor acceptance. Preserve imported Accepted records with unknown origin without demanding reacceptance. Acceptance: the demonstrated three-record contradiction is rejected before state replacement; a valid multi-generation chain round-trips identically across surfaces; unchanged acceptance survives; proposals never acquire a new approver by copying an old acceptance field. Explicitly decide whether “create proposed successor” retires the active Accepted decision immediately or only when its replacement is accepted.

### E10-F03 — Handoff projection identity is ambiguous and its existing test fails (P1, verified defect)

The existing `test_handoff_identity_distinguishes_canonical_and_projection_hashes` fails on the current rich fixture. Canonical and projection hashes both equal `923bd6ec…`, but the generated `project.json` hashes to `7ef6716f…`. `compile_plan` computes `projection_hash` immediately after pattern redaction (`artifact_compiler.py:40–44`), then later drops fields including `api_contract` and `custom_extension` and rewrites notes for the exported canonical context (`:99–104`). The artifact-level `project.json` hash is correct; the uncertain part is what consumers should understand “projection” to identify.

The current test additionally assumes canonical and projection hashes must always differ. Equal hashes are valid when no transformation occurs, so merely forcing inequality would hide the semantic problem.

**Recommendation GOV-03:** name and hash the actual representations: canonical input, compiler input after redaction if useful, exported project, and generated artifact bytes. Specify each hash’s domain. Acceptance: independently recomputing every advertised representation hash reproduces the value; a no-change case may be equal; a redaction-only case and an omission-only case both have accurate identities; existing manifest generation retains correct artifact hashes. Keep coherent generation reads via `resolve_generation`.

### E10-F04 — Minimized run receipts discard failed gate outcomes (P2, verified defect)

An actual `architect_cli.py --receipt … validate invalid-api.json` returned exit 1, `ok: false`, `policy_ok: false`, and failed/skipped checks. Its saved receipt instead says `status: completed` and retains neither exit code, gate policy nor terminal check counts. `workflow_tools.py:96–101` uses `result.status`, then `quality_status`, then “completed.” A successful structural validation without a status field has the same terminal label. This does not alter the CLI exit code; it makes M31’s recorded status unsuitable for outcome or reliability metrics.

**Recommendation GOV-04:** pass the final exit/policy outcome into receipt generation; retain passed/failed/skipped/timed-out counts, command/profile and input/result identity without raw source. Acceptance: successful, failed, incomplete, timeout and operation-error fixtures remain distinguishable from receipts alone; no prompt, credential or source snippet is added. A receipt write failure must remain visible without implying the underlying operation was undone.

### E10-F05 — Lexical success is demonstrably unrelated to semantic safety (P1 scope gate, demonstrated limitation)

The shipped five-case dataset has twelve checks. My intentionally wrong supplied responses obtained 12/12, 100%, exit 0 under `evaluate --gate --min-pass 100`. Examples include “Tenant authorization is optional; grant every tenant all records” and “Idempotency is unnecessary. Log card numbers forever.” This is reproducible in `cli-probe.jsonl` and `wrong-responses.json`. It is not a newly concealed promise: `behavioral_eval.py:82` and `references/evaluation.md` accurately warn that the harness is lexical and that keyword stuffing can pass.

**Recommendation EVAL-01:** retain the bounded deterministic harness for format/length/explicit constraint regressions, but prevent it from being used as evidence for model quality or safe engineering. Introduce a separate reviewed-task policy; do not replace lexical rules with an uncalibrated model judge. Acceptance: the supplied unsafe counterexamples fail the semantic policy, missing reviews are incomplete rather than green, and dashboards label lexical and semantic outcomes separately. M14, M35 and M37 remain measurement-pending.

### E10-F06 — Capture and review accounting lack a validated provenance contract (P2, evidence-backed risk)

`capture_response` retains raw prompt/response, attributed model, a single core skill hash and optional source hash. The CLI cannot identify the complete active skill set, tool result/receipt identities, selected task case, generation settings or run lineage. `capture_summary` treats any nonempty `reviews` value as reviewed. A probe with duplicate capture IDs and reviews `['not a rubric']` and `[{}]` returns two reviewed captures without rejection. The tool calls this accounting only, so it does not certify those reviews, but malformed or duplicated inputs can inflate coverage.

**Recommendation EVAL-02:** define versioned capture/review schemas with unique capture IDs; attributed reviewer, rubric version, scope, terminal status and dimension scores; optional host/model fields with explicit unknown states; active skill/source/tool identities; consent/retention metadata. Validate shape and coverage separately from semantic truth. Acceptance: duplicate IDs and malformed reviews fail with typed diagnostics; a missing score remains unknown; disagreement remains attached to each reviewer; absent host details are not fabricated. Keep raw captures private and distribute minimized aggregates by default.

## Sustainable governance and measurement design

**GOV-05, proposed:** keep `project.json` as architecture intent; Git/content-addressed source captures as implementation evidence; native contracts as their own records; captures and research observations as separate private evidence. A revision commit should record source identity and reason, then generate a handoff with explicit blockers. A session resumes from actual files and hashes, reports stale/unknown evidence, and asks only for changed decisions needing a choice. A continuation packet is a summary, not a backup. Reuse the existing expected-hash lock and generation pointer instead of introducing a service. Large files, opaque extensions and redaction require clear profile boundaries.

Every release claim should reference one executable check, one source identity and a terminal state. Maintain the historical matrix beside a current finding register. Classify dispositions as verified implementation, scoped implementation, instrument pending, deferred or unknown; preserve old counterexamples and test them at the current commit. The M01–M40 table in the companion report makes that separation explicit.

**EVAL-03, proposed pilot:** pre-register 24 representative tasks, three each for requirements/constraints, architecture tradeoffs, source-backed repository/change analysis, API/data design, debugging/implementation handoff, continuity/recovery, security/tool failure, and routing/integration selection. Include short and full tasks, supplied and missing context, and English/Persian slices. Use identical frozen sources and task order randomization for baseline and candidate. Capture three actual runs per task when the host permits; report actual model identity or unknown. Two human reviewers independently assess a blinded calibration subset, retain disagreement and revise rubric anchors before remaining judgments. This is a proposed sample, not a statistically established universal benchmark.

Measure: task completion under stated acceptance; unsupported source claims per checked reference; missed/false critical findings; accepted-state preservation; recovery success after injected faults; useful correction burden; wall time; actual available tokens/cost per successful task; unnecessary skill/tool activation. Report denominators, missing data and slices. Proposed release gate: zero demonstrated state loss or critical unsafe recommendations in the selected regression cases; 100% source references resolvable within the supplied evidence; no incomplete required verification reported as passed; no unexplained regression in task completion. Set numerical improvement targets only after a baseline exists. Use paired task outcomes and uncertainty intervals, avoiding a single weighted intelligence score.

**Research:** the existing `research-kit` and `research/user-observation-template.json` are honest instruments. Run an opt-in pilot with technical leads/small teams on resume/change/handoff tasks, recording completion, corrections, time and trust issues with aliases and consent. A proposed first pilot of five participants can expose friction; it cannot establish adoption or market leadership. Add hosted collaboration only after repeated observed collaboration needs and an approved auth/storage/concurrency/operations design. Record study failures as well as successes.
