## Disputed inferences and practical constraints

**Cache trust does not require cryptographic infrastructure.** E04 demonstrates accidental semantic loss without an attacker and should lead with that. Cache keys include current content hash, root and toolkit version (`repository_evidence.py:123–134`), but editable cached declarations are not authenticated. Do not infer authenticity from those identities or turn a local opt-in cache into a signed evidence service. Validate full bounded entry shape/status and adapter configuration; use a private cache location, or disable/recompute for higher-trust workflows. Signatures would not make parser conclusions true. An adversary able to rewrite both local source and cache is a different threat model requiring explicit host/storage controls.

**Keep priority and measurement proportional.** E04-F03 generic change seeds and optional-record output are valuable, independently corroborated by my probes; requirement-only public impact syntax limits the current promise. Treat as P2 for today's scoped tool, P1 before generalized automated change handoffs. E05's 30-task benchmark/80% threshold is a useful proposed pilot, not a validated release criterion; do not block deterministic integrity repairs on conducting it. Likewise lack of native application generation means generation quality is unmeasured, not failed. Missing optional real rendering should block an applicable render claim, not every quick architecture answer.

Repeated executions of the same checked-in tests are corroboration of reproducibility, not additional unique tests or statistically independent validation. The shared practical recommendation survives critique: close current integrity defects, preserve local recovery/portability, and prove one thin host-backed edit/check workflow before platform expansion.
