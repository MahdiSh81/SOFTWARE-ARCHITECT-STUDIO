# Prioritized implementation roadmap — proposed, not authorized

Repair the existing local product before expanding execution authority. Estimates below are planning ranges in focused engineer-days for one engineer familiar with Python/JS and existing tests; they include implementation/review/regression work but exclude plugin approval queues, provider access, actual participant recruitment and production rollout. They are not measured costs or delivery promises. Each slice must retain working CLI/browser behavior and be reviewable independently.

All initiatives follow this shared implementation contract: characterize retained counterexamples before changing code; preserve user data and Accepted facts; scope edits to affected components; use actual host permission; install no implicit new service; version any changed public contract; validate on exact source; preserve blocked/partial states; rollback to the prior package without rewriting canonical data. Tests and expected outcomes are attached to each canonical finding in `finding-register.md`, detailed expert report and the named specification. A later implementation request supplies authorization; this audit does not.

## Milestones and dependency order

M-A: I01 plus the data-loss and contract-integrity slices of I02–I06 establish truthful local release evidence. No claim of an end-to-end coding product is made at this milestone.

M-B: remaining I02–I06 conformance/coverage and minimal I07 seams make local intent/export/recovery/evidence dependable. Each patch brings its counterexample and relevant regressions; do not wait until the end for a bulk testing phase.

M-C: I08 and the I09 read-only/propose/check proof connect one host without granting write authority. Then demonstrate authorized apply/recovery on an isolated fixture. This is the first evidence that could support a connected program-creation claim.

M-D: I10 selected integrations and I11 measured skill/user outcomes justify expansion. User studies and model evaluation are ongoing evidence work, not a final checkbox after shipping. I12 requires a separate case and approval.

## Prioritization rationale

Data preservation, source/contract identity and false-green prevention outrank feature breadth. Value/effort estimates are qualitative: I01–I06 close demonstrated defects with bounded code changes; I09 adds high value but increases authority and test complexity; I10 depends on a real language/provider need; I12 has unproven value and highest operating cost. An unavailable plugin listing never advances an integration milestone. No arbitrary priority score replaces critical security/data-integrity gates.
