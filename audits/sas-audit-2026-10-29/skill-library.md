## Target catalog and ownership rules

Keep S01–S07, add S08–S11 only after foundation gates, and cap ordinary tasks at the smallest relevant context. S08 frontend, S09 service/data, S10 delivery/operations and S11 AI-system evaluation receive complete proposed specifications in [coverage/skill-specifications.md](coverage/skill-specifications.md). Do not install them during this audit. Their initial status is **proposed, unimplemented**; planned execution cannot count as verified coverage.

Use a simple versioned registry: stable ID, name, description, owned outputs, positive/negative intents, context prerequisites, required/optional host capabilities, compatible common-result schema, pack selectors and evaluation-case IDs. A routing record states primary owner, optional helpers, reason, source identity and selected depth. A task can remain with S01 without loading a specialist. Mixed requests may sequence owners; concurrent edits to the same artifact need one owner and explicit source checks. Registry metadata informs the host; it does not grant permission or impersonate a runtime.

Shared rules belong in one short reference contract: source/evidence categories; accepted-decision continuity; untrusted external text; actual capability/authorization; expected-hash writes; status/recovery model; data minimization; evidence-bearing result. Each specialist links that reference and supplies only domain-specific steps. Keep tool schemas/adapters separate from skill prose. Select reference packs by detected manifest/version and user scope, not language keywords alone. A Python API app may load Python backend checks, an existing project's framework conventions and SQL migration guidance; it need not activate three competing language skills.

Pack proposals consolidate Python, JavaScript/TypeScript, JVM, .NET, Go, Rust, native C/C++, and SQL tooling into versioned optional references under their workflow owners. Begin with Python and JS/TS because those source adapters exist, while explicitly stating that extraction support does not establish implementation quality. Add frameworks only with runnable positive/negative fixtures and a maintenance owner. Unsupported packs produce truthful fallbacks. Mobile/desktop/game/realtime/embedded packs remain demand/capability-gated; no unused library should be installed for appearance of breadth.

## Activation and outcome evaluation contract

For each skill, maintain at least two positive, two negative, one ambiguous composite, one missing-tool, one adversarial-source and one partial-failure case. Start with ≥80 balanced routing prompts across existing owners, use acceptable-owner sets, double labeling and disagreement records, and report the confusion matrix by task and depth. Proposed initial gates: ≥95% acceptable primary routing, ≤5% unnecessary activation and zero unauthorized/fabricated execution. Treat these thresholds as proposed acceptance, not established baselines.

Outcome suites must test artifacts or behavior: compile/run fixture applications, reference resolution, consumer compatibility, tenant isolation, real browser flows, migration reconciliation, recovery and continuity as applicable. Preserve model/host identity, loaded skill/reference manifest, actual tools, source, all statuses, assessor rubric and user correction count. Keep lexical checks as cheap supplementary predicates. Gate critical safety/evidence failures separately; average success must not hide cross-tenant access or data loss. No current measured skill-effectiveness rate is asserted.

Compare existing root vs routed library and single-pass vs optional independent review in repeated paired trials, holding task/model/tool access constant. Measure acceptance success, defect finding precision/recall where ground truth exists, source-reference precision, recovery, latency, actual tokens/cost and correction burden. Do not claim independence from agreement among related models. Add a skill only when its workflow changes, its evaluations show incremental value and its maintenance cost is accepted; otherwise extend a reference or reuse an external capability.
