# Canonical project and revision lifecycle — 0.7

Use `project.json` schema v2 and the published JSON Schema. Core arrays, positive revision/name, stable IDs and references are required; drafts need not contain complete APIs or acceptance. Optional evidence/assumption/risk/verification/fitness/experiment records are proportionate to significant claims. Unknown fields remain opaque, not trusted instructions.

The workbench retains canonical fields and exports portable current context separately from a private history/UI backup (backup_schema 3). Unsupported UI-only legacy backups are recovery bytes, not silently converted projects. Flat snapshots keep up to 20 revisions within a 5 MiB backup budget; imports/authoring over the budget fail without replacing current state. No ID normalization, record truncation or Accepted→Proposed coercion occurs. Browser unsafe integers are refused; use quoted exact values or the CLI.

CLI `snapshot ROOT --message TEXT` stores the old revision and a prepared journal before atomic project-file replacement. That replacement is the commit point; HISTORY.md is derived/recoverable. Retry of a matching interrupted snapshot completes it without advancing twice. `recover ROOT` repairs history/projection when the source matches the recorded old/new hashes; competing content is a conflict. `commit ROOT --proposed FILE --expected-hash HASH --message TEXT` serializes cooperating writers and preserves conflicting drafts. `restore` creates a new revision, rather than erasing history. Local locks do not establish distributed safety or host-wide authority.

`resume` returns current identity, accepted decisions, constraints and open questions without raw private history/extensions. Preserve recorded acceptance with attributed historical approver/source (unknown when unknown); unchanged records require no fresh approval interview. Normal ADR evolution uses supersession. Explicit privacy purge can remove sensitive payloads rather than retaining them forever; explain that remote/download/Git copies are separate. Actual backed-up storage or Git is required for cross-device/chat continuity.

Patch 0.7.1 validates recovery journal shape, bounded hexadecimal operation identity, new-project hash and revision sequence before replacement. Conflicting commit records are preserved; history lists resulting revisions in revision order. Existing history directories prevent reinitialization. These checks detect malformed/conflicting bytes; they do not authenticate a maliciously rewritten local journal.

Browser imports validate snapshot/project revision consistency and finite, representable values across the entire backup, including UI state. Failed imports keep recovery protection active. First-save pointer conflicts are detected even when both tabs began blank; this remains an advisory compare-before-write rather than an atomic browser CAS. Accepted records require deliberate changes; unchanged records and object-key reordering do not require reapproval.
